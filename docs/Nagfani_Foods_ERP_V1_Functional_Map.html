3. Core Business Logic Engines & Mathematical Foundations

3.1 Multi-Godown Stock Engine

CRITICAL SYSTEM RULE: Stock quantities in stock_levels are NEVER directly overwritten or updated via direct arithmetic. Every inventory change MUST be written as an immutable document in stock_movements wrapped inside a MongoDB session transaction.

The state of inventory for any item in any godown is governed by the following mathematical identity:

  Available Stock = Physical Stock - Reserved Stock
Movement TypePhysical EffectReserved EffectAvailable EffectTriggering Business Event
purchase+ qty0+ qtySupplier purchase invoice receipt confirmed.
production_in+ qty0+ qtyManufacturing batch completed & packed.
consumption- qty0- qtyRaw material consumed in recipe batch.
reserve0+ qty- qtyCustomer sales order booked in "received" status.
release0- qty+ qtyOrder cancelled or line items deleted.
pack000Warehouse packs goods into delivery staging bay.
ship- qty- qty0Delivery van departs warehouse with consignment.
transfer_out- qty0- qtySource godown in godown-to-godown transfer.
transfer_in+ qty0+ qtyDestination godown in godown-to-godown transfer.
adjustment± qty0± qtyAudit adjustment (physical count recount).
wastage- qty0- qtyDamaged goods, expired packets, frying residue.

3.2 Order Lifecycle & State Machine

  [Draft / New Order Entry]
             │
             ▼
      ( 1. RECEIVED ) ──[Order Booked]──> Reserves inventory (Reserved +qty, Available -qty)
             │
             ▼
      ( 2. PACKED )   ──[Staged at Bay]─> Physical & Reserved stay intact; order locked from user edit
             │
             ▼
      ( 3. SHIPPED )  ──[Van Departs]───> Physical stock deducted (Physical -qty, Reserved -qty)
             │
             ▼
      ( 4. DELIVERED )──[Customer Receives / COD Collected]──> Triggers Invoice & Payment entry
             │
             ▼
      [ 5. INVOICE ISSUED & TALLY SYNCED ]

  * CANCEL GUARD: Order can be cancelled ONLY from 'RECEIVED' or 'PACKED'. Once 'SHIPPED', cancel is blocked.

3.3 Customer Rate-Memory Algorithm

When an order line item is added, the system automatically suggests the pricing for that specific customer using a strict fallback hierarchy:

  1. Customer Historical Rate: Queries rate_history for partyId + itemId sorted by date: -1. If found, returns the most recent agreed rate.
  2. Item Standard MRP: If no prior transaction exists for that customer, defaults to the item's mrp from items.
  3. Item Standard Cost: If MRP is undefined, falls back to standardCost or base Rs 100.

3.4 Recipe BOM Batch Scaling & Manufacturing Variance

Recipes are defined for a standard base batch (typically 100 kg or 100 packs). During production entry, quantities are dynamically scaled:

  Theoretical Line Qty = BOM.baseLineQty * (ActualBatchProducedQty / BOM.baseQty)
  Variance = ActualConsumptionQty - TheoreticalLineQty

Accounting & Inventory Impact: In a single atomic transaction:

  • Each raw material item has a consumption movement logged (godown physical stock decreases).
  • The finished goods item has a production_in movement logged (godown physical stock increases).
  • If wastage > 0, a wastage movement is logged on the finished product.
  • A Manufacturing Stock Journal entry is enqueued to sync_outbox for TallyPrime posting.

3.5 Customer Running Balance Ledger & Payment Mechanics

Customer accounts use an open-item running balance calculation:

  Invoice Generated (Debit)  ──> Balance increases (+ Grand Total)
  Payment Recorded (Credit)  ──> Balance decreases (- Paid Amount)
  Net Ledger Balance         ──> Current Receivable (Outstanding Debt)

For suppliers, the polarity is inverted: purchase bills credit the supplier account (increasing accounts payable, represented as a negative balance).

5. Exhaustive REST API Route & Controller Specification

All endpoints are prefixed with /api/v1 and enforce strict JWT authentication unless marked public.

5.1 Authentication Controller (/api/v1/auth)

POST/api/v1/auth/login
Access: Public · Rate Limit: 10 req/min · Auth: None

Authenticates user via username, email, or 10-digit mobile number and returns signed JWT token.

Request:  { "username": "admin", "password": "secure_password" }
Response: { "success": true, "token": "eyJhbG...", "user": { "id": "...", "name": "Admin", "role": { "code": "ADMIN" } } }
GET/api/v1/auth/me
Access: Authenticated · Auth: Bearer JWT

Returns the currently authenticated user session details, role, and mustChangePassword flag.

POST/api/v1/auth/change-password
Access: Authenticated · Auth: Bearer JWT

Updates user password. Verifies current password before hashing new password with bcrypt.

5.2 Orders Controller (/api/v1/orders)

GET/api/v1/orders
Access: Order, Packing, Delivery, Accounts, Admin · Query: status, areaId, segment, search, fromDate, toDate

Retrieves paginated orders with populated party, area, and godown metadata.

POST/api/v1/orders
Access: Order, Admin · Permission: order.create · Transaction: Yes

Books new customer order. In an atomic transaction: checks stock availability, auto-generates orderNo (e.g. ORD-000123), auto-generates B2C Delivery Challan number (DC-000125), computes line-level GST, logs reserve stock movements, enqueues sync_outbox, and emits order:created via Socket.IO.

Request:  { "partyId": "...", "godownId": "...", "items": [{ "itemId": "...", "qty": 10, "rate": 140 }], "paymentTerms": "COD" }
Response: { "success": true, "data": { "orderNo": "ORD-000123", "status": "received", "grandTotal": 1400 } }
POST / PATCH/api/v1/orders/:id/status
Access: Role-guarded · Transaction: Yes · Sockets: order:status

Transitions order lifecycle status. Enforces strict transitions:

  • packed: Marked by Packing role; verifies staging without modifying stock reserve.
  • shipped: Marked by Delivery/Admin; invokes shipOrderStock() reducing physical inventory.
  • delivered: Marked by Delivery/Admin; finalizes delivery and updates status timeline.
  • cancelled: Blocked if already shipped; releases reserved inventory back to available stock.
POST/api/v1/orders/:id/payment
Access: Delivery, Accounts, Admin · Permission: payment.record · Transaction: Yes

Records cash/UPI collection against an order. Updates order paidAmount, adjusts customer ledger balance, and enqueues Tally Receipt voucher.

5.3 Inventory & Multi-Godown Controller (/api/v1/stock)

GET/api/v1/stock/levels
Access: All Authenticated · Query: godownId, category, lowStockOnly

Returns physical, reserved, and available quantities per item and godown.

POST/api/v1/stock/transfers
Access: Admin, Stock Supervisor · Permission: stock.transfer · Transaction: Yes

Executes godown-to-godown inventory movement. Writes paired transfer_out and transfer_in movements atomically.

POST/api/v1/stock/adjustments
Access: Admin · Permission: stock.adjust · Transaction: Yes

Records physical inventory count correction or wastage write-off with mandatory audit reason.

5.4 Food Manufacturing Controller (/api/v1/manufacturing & /api/v1/boms)

GET/api/v1/boms/for-product/:productId
Access: Order, Production, Admin

Fetches the active recipe BOM for a product to auto-populate theoretical ingredient consumption in production form.

POST/api/v1/production
Access: Production Lead, Admin · Permission: manufacturing.create · Transaction: Yes

Confirms food manufacturing batch. Decreases raw material quantities, increases finished goods, records wastage, computes consumption variance, and creates Tally Stock Journal sync record.

5.5 Billing & Invoicing Controller (/api/v1/invoices)

POST/api/v1/invoices/generate-from-order/:orderId
Access: Accounts, Admin · Permission: invoice.create · Transaction: Yes

Generates sequential Tax Invoice (INV-000123). Computes CGST/SGST/IGST breakdown, debits customer ledger balance, links invoice to order, and queues Tally Sales Voucher.

5.6 Tally Gateway Integration Controller (/api/v1/sync)

POST/api/v1/sync/heartbeat
Access: Connector · Auth: Header x-api-key

Called every 3 seconds by Windows desktop connector. Updates connector online status and Tally reachability flag.

GET/api/v1/sync/pending
Access: Connector · Auth: Header x-api-key · Query: limit

Fetches unposted outbound records from sync_outbox to be converted to XML and posted to TallyPrime port 9000.

POST/api/v1/sync/ack
Access: Connector · Auth: Header x-api-key

Acknowledges successful Tally XML posting. Updates outbox item to synced and records Tally GUID in sync log.

POST/api/v1/sync/inbound-bulk
Access: Connector · Auth: Header x-api-key

Bulk imports customer ledgers, supplier ledgers, and stock items extracted directly from TallyPrime into the ERP cloud database.

8. Bidirectional TallyPrime XML Protocol & Gateway Engine

Gateway Connectivity: TallyPrime runs as an on-premises HTTP web server on http://localhost:9000. The Python Desktop Gateway (distributed as Setup.exe) establishes outbound HTTPS polling to the cloud ERP API, eliminating the need for static IPs, port forwarding, or firewall holes on the client PC.

8.1 Synchronization Protocol & Polling Lifecycle

  1. Heartbeat Ping (Every 3 seconds): Gateway sends POST /api/v1/sync/heartbeat containing Tally port 9000 reachability and current company name.
  2. Outbound Queue Fetch: If Tally is responsive, gateway requests GET /api/v1/sync/pending?limit=20.
  3. XML Transformation: Gateway compiles the JSON domain payload into Tally-compliant XML envelopes using tally_xml.py.
  4. Tally Ingestion: Gateway sends POST http://localhost:9000 with Content-Type: text/xml; charset=utf-8.
  5. Response Parsing & Acknowledgment:
    • If <CREATED>1</CREATED> or <ALTERED>1</ALTERED>: Calls POST /api/v1/sync/ack with Tally GUID.
    • If <ERRORS>>0</ERRORS>: Calls POST /api/v1/sync/fail with exact line error description.
